# 면접 질문·피드백 프롬프트 품질 평가 설계

## 1. 목표

면접 질문과 구조화 피드백 프롬프트를 코드에서 분리하고, 자연스러움·근거성·구체성을 LangSmith 오프라인 평가로 비교한다.

이번 단계에서는 LangChain이나 LangSmith를 운영 애플리케이션의 런타임 의존성으로 추가하지 않는다. 저장소의 프롬프트와 익명화된 평가 데이터가 원본이며, LangSmith는 프롬프트 후보 비교와 LLM Judge 결과 확인에 사용한다.

온라인 평가는 포함하지 않는다. 오프라인 평가 기준이 사람의 판단과 충분히 일치한 뒤 별도 작업으로 검토한다.

## 2. 이번 구현 범위

### 2.1 프롬프트 관리

- `InterviewAiService`에 인라인으로 작성된 첫 질문, 후속 질문, 피드백 프롬프트를 클래스패스 리소스 템플릿으로 분리한다.
- 저장소의 템플릿을 운영 프롬프트의 단일 원본으로 삼고 Git 이력으로 버전을 관리한다.
- LangSmith의 프롬프트는 실험용 사본이며 운영 시 원격으로 가져오지 않는다.
- 현재 질문 SSE 전송 방식, 질문 저장 시점, 피드백 재생성 흐름은 변경하지 않는다.
- Markdown·괄호·질문 문장·인용 원문을 검사하는 운영 Validator는 이번 구현 범위에서 제외한다.

## 3. 프롬프트 개선 방향

생성 모델 `gpt-5.4-nano`가 속한 GPT-5.4 계열의 공식 가이드에 맞춰 candidate를 명시적인 XML 의미 블록으로 구성한다. `role`, `objective`, 입력 해석 규칙, 판단 절차, 출력 계약과 최종 검증을 분리하고, 평가를 통과하는 데 필요한 최소 규칙만 유지한다. 동적 자기소개와 대화는 지시가 아닌 데이터 블록으로 격리한다.

질문 결과는 일반 텍스트 한 문장으로 생성한다. 구조화 피드백 결과는 프롬프트에 JSON 스키마를 반복하지 않고 기존 provider-native Structured Output 계약에 맡긴다. candidate가 승인되어 운영 템플릿으로 승격될 때는 XML 경계를 깨뜨리지 않도록 동적 문자열을 escape한다.

### 3.1 첫 질문

- 포지션, 경력 수준, 면접 유형과 지정 키워드에 맞는 하나의 평가 포인트를 선택한다.
- 자기소개는 난이도와 주제 선택의 참고 자료로만 사용하며, 자기소개에 등장한 세부 경험을 사실로 전제하지 않는다.
- 실제 면접관이 말할 수 있는 자연스러운 한 문장 질문만 반환한다.
- 설명, 평가, 칭찬, 역할 접두사, Markdown을 출력하지 않는다.
- 암기형 함정 질문과 한 문장 안의 복합 요구를 피한다.

### 3.2 후속 질문

- 전체 대화로 질문 중복과 주제의 탐색 정도를 판단하되, 후속 질문의 직접 근거는 지원자의 마지막 답변에서 찾는다.
- 피상적 답변에는 쉬운 구체화 질문, 충분한 답변에는 근거·판단 기준·트레이드오프 질문을 사용한다.
- 현재 주제가 충분히 탐색됐거나 지원자가 답할 수 없는 경우에만 새 주제로 전환한다.
- 한 문장 질문만 반환하고 평가, 칭찬, 역할 접두사, Markdown을 출력하지 않는다.

### 3.3 피드백

- 모든 판단은 지원자의 실제 답변에 근거하고, 답변에서 확인할 수 없는 경력·성과·성향을 단정하지 않는다.
- 강점과 개선점은 근거가 된 질문 번호와 연결한다.
- `quote`는 실제 지원자 답변의 연속된 원문만 사용하며 수정하거나 합성하지 않는다.
- 4축 점수의 평가 기준을 구체화하고 점수, 코치 브리핑, 강점과 개선점 사이의 일관성을 자체 점검한다.
- 사용자 노출 문자열은 일반 텍스트로 생성한다.
- Free, Basic, Pro의 생성 범위와 null·목록 계약은 현재 정책을 유지한다.

## 4. LangSmith 오프라인 평가

### 4.1 데이터셋

익명화 실제 사례와 합성 경계 사례를 JSONL로 저장소에 커밋한다. 개인·회사·프로젝트를 식별할 수 있는 이름, 연락처, 계정 식별자와 고유 서술은 제거하거나 일반화한다.

- 첫 질문 15건
- 후속 질문 25건
- 피드백 20건

각 예시는 고유 `caseId`, 대상 종류, 입력, 출처 구분(`ANONYMIZED` 또는 `SYNTHETIC`), 태그, 반드시 만족할 기준, 금지할 오류를 가진다. 정답 문장 하나를 강제하지 않고 허용 가능한 품질 기준을 기록한다.

### 4.2 Judge 모델

- 생성 모델 `gpt-5.4-nano`와 분리된 상위 모델을 사용한다.
- 1차 Judge는 `gpt-5.5`로 고정하고 동일한 모델 버전과 설정으로 baseline과 candidate를 평가한다.
- LangSmith 계정에서 해당 모델을 사용할 수 없는 경우 실험을 실행하지 않고 모델 접근 권한을 먼저 해결한다. 임의로 다른 Judge 모델로 대체하지 않는다.
- LangSmith UI의 LLM-as-a-Judge 평가기 하나는 하나의 feedback key를 저장하므로, 대상별 품질 평가기와 중대 오류 평가기를 분리한다.
- 품질 평가기는 아래 세부 축을 내부 루브릭으로 모두 검토한 뒤 `1~5`의 종합 점수 하나와 짧은 근거를 반환한다. 100점 척도는 Judge가 구분하기 어려운 미세한 점수 차이를 만들고 면접 결과 점수와도 혼동되므로 사용하지 않는다.
- 중대 오류 평가기는 별도 feedback key로 오류 여부와 오류 코드를 반환한다. 치명적인 오류가 종합 평균에 가려지지 않게 하기 위한 분리다.
- 5점 척도의 공통 기준은 다음과 같다.
  - 1점: 사용할 수 없거나 중대 오류가 있는 결과
  - 2점: 여러 핵심 기준을 위반한 결과
  - 3점: 사용할 수 있지만 명확한 수정이 필요한 결과
  - 4점: 운영에 사용할 수 있고 사소한 개선만 필요한 결과
  - 5점: 모든 핵심 기준을 충족하는 우수한 결과

### 4.3 질문 평가 기준

공통 평가축:

- `relevance`: 포지션·경력·면접 유형 적합성
- `singleFocus`: 하나의 평가 포인트만 질문하는지
- `clarity`: 범위와 요구 답변의 명확성
- `naturalness`: 실제 면접 질문으로서의 자연스러움
- `answerability`: 지원자 수준에서 답할 수 있는지

첫 질문에는 `keywordAlignment`를 추가한다. 후속 질문에는 `contextGrounding`, `progression`, `transitionQuality`를 추가한다.

다음은 중대 오류다.

- 둘 이상의 질문을 결합함
- 질문이 아닌 평가·설명을 출력함
- 답변에 없는 사실을 지원자가 말했다고 전제함
- 이전과 동일하거나 사실상 같은 질문을 반복함
- 역할 접두사 또는 금지된 칭찬 표현을 출력함

### 4.4 피드백 평가 기준

- `groundedness`: 실제 답변 근거성
- `specificity`: 지원자 답변에 특화된 구체성
- `actionability`: 다음 답변에서 실행 가능한 개선점인지
- `scoreConsistency`: 점수와 서술의 일관성
- `evidenceAlignment`: 인용과 해석의 일치
- `readability`: 괄호 남용 없이 자연스럽고 읽기 쉬운지
- `tierFitness`: 플랜별 정보량과 깊이의 적합성

다음은 중대 오류다.

- 지원자가 하지 않은 말을 근거로 평가함
- 인용을 조작하거나 다른 답변에 잘못 연결함
- 확인할 수 없는 경력·성과·성향을 단정함
- 점수와 설명 또는 강점과 개선점이 명백하게 모순됨
- 차별적이거나 면접과 무관한 기준을 사용함

### 4.5 실험과 승인

- 기존 프롬프트를 baseline, 개선 프롬프트를 candidate로 동일 데이터와 동일 생성 설정에서 실행한다.
- 절대 점수 평가와 함께 프롬프트 이름을 숨기고 A/B 표시 순서를 무작위화한 pairwise 평가를 수행한다.
- 형식 위반과 중대 오류는 0건이어야 한다.
- 첫 질문, 후속 질문, 피드백의 종합 품질 평균은 각각 4.0/5 이상이어야 하고 baseline보다 하락하지 않아야 한다.
- candidate가 패배한 사례, Judge가 중대 오류로 분류한 사례, 점수 차이가 큰 사례는 사람이 모두 검토한다.
- 자동 기준을 통과하고 사람 검토에서 승인된 candidate만 운영 리소스 프롬프트로 반영한다.
- 실험 메타데이터에는 Git commit, 프롬프트 식별자, 생성 모델·설정, Judge 모델·설정을 기록한다.

LangSmith 공식 문서의 dataset → evaluator → experiment → comparison 흐름을 따르되, 운영 애플리케이션은 LangSmith에서 프롬프트를 가져오거나 운영 trace를 전송하지 않는다.

새 평가는 기존 LangSmith 데이터셋·프롬프트·평가기 설정을 덮어쓰지 않고 다음 여섯 개의 v2 평가기로 만든다.

- `first_question_quality_v2`, `first_question_critical_failure_v2`
- `follow_up_question_quality_v2`, `follow_up_question_critical_failure_v2`
- `feedback_quality_v2`, `feedback_critical_failure_v2`

초기에는 종합 품질 평가기의 근거에서 취약한 세부 축을 확인한다. 특정 축의 오판이나 회귀가 반복될 때만 그 축을 독립 평가기로 분리한다.

## 5. 테스트와 완료 기준

### 운영 코드 테스트

- 텍스트 리소스로 분리한 프롬프트에 기존 입력값과 티어별 계약이 누락 없이 주입된다.
- 리소스화 전후의 AI 호출 방식, 질문 SSE 계약과 피드백 생성 흐름이 유지된다.

### 평가 완료 기준

- 60개 JSONL 예시가 개인정보 검토를 통과한다.
- baseline과 candidate가 동일 조건으로 LangSmith에서 실행된다.
- candidate가 보수적 자동 기준을 통과한다.
- 자동 평가에서 검토 대상으로 분류된 사례의 사람 검토가 완료된다.
- 최종 운영 프롬프트와 승인된 candidate의 내용이 일치한다.

## 6. 제외 및 후속 작업

- 운영 요청의 LangSmith trace 수집과 온라인 평가는 제외한다.
- 평가 실패만으로 이미 생성된 운영 결과를 폐기하는 실시간 LLM Judge는 도입하지 않는다.
- Markdown·괄호·질문 문장·피드백 인용 원문을 코드로 검사하는 운영 Validator는 후속 구현 범위로 분리한다.
- 질문 Validator를 도입할 때는 `SSE를 유지하며 전체 결과를 버퍼링할지`, `검증 없이 스트리밍할지`, `동기 JSON API로 교체할지`를 응답 시간 측정 후 다시 결정한다. 현재 논의한 최대 3회 재생성과 180초 timeout은 확정 정책으로 보지 않는다.
- 피드백 Validator는 기존 구조 검증과 합칠지 일반 텍스트 검증기로 분리할지 후속 설계에서 결정한다.
- Judge와 사람 평가의 일치도가 확인된 후, 개인정보 제거와 샘플링 정책을 별도 설계해 온라인 평가를 검토한다.
- 초기 평가축은 본 문서의 항목으로 제한하고, 반복되는 미탐지 실패 유형이 확인될 때만 추가한다.
